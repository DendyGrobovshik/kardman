# Modules Architecture

Each Gradle module and the role it plays in the RDMA pipeline. For the runtime
data flow and threading model, see [architecture.md](architecture.md).

## Modules

### `:rdma-annotation`

Minimal KMP module with the `@RDMA` annotation:

```kotlin
@Target(AnnotationTarget.CLASS, AnnotationTarget.FUNCTION)
@Retention(AnnotationRetention.RUNTIME)
annotation class RDMA
```

Targets: JVM, JS, iOS. Retention `RUNTIME` is required so the compiler plugins
can find the annotation in compiled dependencies. It is applied both to `@RDMA`
classes and to `@Composable` widget functions.

### `:rdma-types`

Shared, `@Serializable` metadata model exchanged between the two compiler
plugins. Defines `RdmaClassInfo`, `RdmaFunctionInfo`, `RdmaParameterInfo`,
`RdmaType`, `StaticInfo` and the top-level `RdmaManifest` (classes + functions).
The kernel compiler plugin serializes this model into `rdma_manifest.json`; the
plugin compiler plugin deserializes it to know exactly which classes/functions
are bridgeable.

### `:kernel`

Contains `@RDMA` annotated classes (shared data types) and the `@Composable`
UI widgets. JVM module with material3 + Compose runtime.

```kotlin
@RDMA
class Person(val name: String, val age: Int) {
    override fun toString() = "Person(name='$name', age=$age)"
}
```

The **kernel compiler plugin** (`:rdma-kernel-compiler-plugin`) runs on this module to:
1. Extract class metadata (name, constructors, methods, properties) from the module IR
2. Generate C++ JNI/JSI glue code + `rdma_manifest.json` manifest
3. Inject the vtable dispatch (`__vtable` field + dispatch in `open` methods) directly into IR
4. Extract `@RDMA` top-level functions (widgets and plain functions) into `rdma_manifest.json`

### `:rdma-kernel-compiler-plugin`

An IR compiler plugin (`IrGenerationExtension`) that scans `@RDMA` classes and generates:

| Output | Content |
|--------|---------|
| `RdmaJniCache.h/cpp` | Struct with cached `jclass`, `jmethodID` for each @RDMA class |
| `{Class}Proxy.h/cpp` | JSI `HostFunction` wrappers for properties and methods + `{Class}NativeState` |
| `RdmaBridge.h/cpp` | `installUserBridge()` — registers all factories in `global.RDMA` |
| `RdmaComposerProxy.h/cpp` | Generated `ComposerProxyHost` + JNI cache for the base Compose protocol |
| `rdma_manifest.json` | Unified JSON manifest of all `@RDMA` types (classes + functions) |
| `RdmaWidgetBridge.h/cpp` | One JSI `HostFunction` per widget (`RDMA.composeXxx`) + widget JNI cache |
| `RdmaWidgetEntries.kt` | One `@Composable` host-side entry per widget (runs in `rdma-runtime-android`) |
| `__vtable` field + dispatch | Injected into each @RDMA class's `open` methods (in-place IR) |

The `{Class}Proxy.*` files use the **NativeState pattern**: instance data (the
JVM `jobject` global ref) lives in a `jsi::NativeState` subclass, while property
getters/setters and methods are prototype `HostFunction`s that pull the pointer
back via `getNativeState()` + `static_pointer_cast`. No `jsi::HostObject` is
involved for data classes — that's reserved for the Compose protocol proxies.

Generated C++ follows the JNI caching pattern:
- `FindClass` + `GetMethodID` called once at init
- Subsequent calls use cached `jmethodID` (O(1) lookup)
- `NewGlobalRef` ensures JVM object survives across native boundaries

The `rdmaVtableDispatch` external declaration is generated by `:rdma-kernel-gradle-plugin` (a static file written before compilation). Synthetic compiler properties (e.g. `$stable` injected by the Compose compiler) are excluded from extraction.

The **Composer proxy** (`RdmaComposerProxy.h/cpp`) is generated from
`RdmaComposerProtocol.baseProtocol` (a version-locked list of `Composer` methods) and
**always** regenerated, independent of any `@RDMA` class. Before generating, the plugin
cross-checks the list against the resolved `androidx.compose.runtime.Composer` IR and
fails the build if a method is missing (compose-runtime version drift). The proxy is
consumed by the static `RdmaCompose.cpp` bridge (`installRdmaComposeBridge`), which keeps
`StateProxyHost`/`ScopeUpdateScopeProxyHost`, the RDMA protocol functions and the JNI
invoke entry points, and delegates all `Composer` method dispatch to the generated proxy.

### `:rdma-kernel-gradle-plugin`

Gradle wrapper (`KotlinCompilerPluginSupportPlugin`) that applies
`:rdma-kernel-compiler-plugin` to `:kernel`'s JVM compilation. It writes the static
`rdmaVtableDispatch` external declaration (`RdmaVtable.kt`) up-front — the compiler
plugin can't add sources to its own pass — and passes the output directories
(`cppOutputDir`, `jsonOutputDir`, `kotlinOutputDir`).

### `:rdma-plugin-compiler-plugin`

A Kotlin FIR compiler plugin that resolves and rewrites plugin source code. It runs as a "resolve" pass over the plugin's original source (compiled against `:kernel` on the JVM) and emits rewritten `.kt` files into `build/generated/rdma/`.

It uses `FirAdditionalCheckersExtension` to inspect the fully-resolved FIR tree and `IrGenerationExtension` as the flush point:

1. Removes `import com.example.kernel.X` lines (matched by qualified name from `rdma_manifest.json`).
2. Replaces `Person("str", 42)` → `js("RDMA.createPerson('str', 42)")` using the resolved constructor's class.
3. Replaces `.name` → `.getName()`, `.status = v` → `.setStatus(v)` using the resolved property's containing class (works for subclasses too).
4. Replaces `class Cyborg(...) : Person(...) { override fun ... }` with `js("""RDMA.createWithOverrides('Person', [...], { ... })""")` and removes the class declaration.
5. Rewrites `@RDMA`+`@Composable` widget calls to generated bridge functions (`Text(...)` → `rdmaText(...)`), and `runRdmaApp`/`mutableStateOf` → `rdmaRunApp`/`rdmaMutableStateOf`.
6. Rejects compose symbols outside the base protocol (`ComposeAllowlist`): any call or import of `androidx.compose.*` that is not `Composable`/`remember`/`mutableStateOf`/`getValue`/`setValue` is a compile error.

Method calls on `@RDMA` receivers pass through unchanged (dynamic dispatch on the JS proxy).

### `:rdma-plugin-gradle-plugin`

Gradle wrapper (`KotlinCompilerPluginSupportPlugin`) that applies `:rdma-plugin-compiler-plugin` to the plugin module's JVM resolve compilation. It:
- writes the static guest-side bridge `RdmaRuntimeBridge.kt` (the `external object RDMA` + `rdmaRunApp`/`rdmaMutableStateOf` helpers) into `build/generated/rdma`,
- passes `rdmaManifest` / `rdmaOutputDir` options.

The per-widget `rdmaXxx` bridge stubs (`RdmaWidgetBridge.kt`) are generated by the
compiler plugin itself into the same directory.

### `:rdma-runtime-android`

Android Library (AAR) containing:

**Kotlin layer:**
- `RdmaBridge.kt` — `System.loadLibrary("rdma_runtime")` + `external fun nativeInit()` / `nativeEvalAsset(String)` / `nativeIsReady()`
- `RdmaComposeHost.kt` — host-side `Content()` and `nativeInvokeScopeBlock`/`nativeInvokeCallback` marshaling

**C++ layer** (`src/main/cpp/`):
- `RdmaJni.cpp` — JNI entry points
- `RdmaRuntime.cpp` — Hermes init (`facebook::hermes::makeHermesRuntime()`), `installRdmaComposeBridge()`, `console`/`globalThis` stubs
- `RdmaRendezvous.cpp` — the UI↔Hermes two-thread rendezvous (see [architecture.md](architecture.md#threading-model-dedicated-hermes-thread))
- `RdmaCompose.cpp` — base Compose protocol (`StateProxyHost`, `ScopeUpdateScopeProxyHost`, compose op dispatch)
- `generated/RdmaComposerProxy.cpp` — generated `Composer` proxy (from the kernel compiler plugin)

**Dependencies:** `hermes-android` (prefab), `fbjni` (prefab).

**Build process:**
1. Kernel compiler plugin runs → generates C++ files in `kernel/build/generated/rdma/cpp/`
2. The app module (via the `rdma-app` Gradle plugin) copies the *user* generated files
   (everything except the framework-owned `RdmaComposerProxy.*`) into
   `androidApp/build/generated/rdma/cpp/generated/`
3. The app's CMake (generated by the same plugin) compiles those + `UserBridgeJni.cpp`
   into `librdma_user.so`, linking against `librdma_runtime.so` (via the
   `rdma-runtime-android` prefab) and `hermes-engine::hermesvm`
4. `UserBridge.nativeInstall()` registers `installUserBridge` through the runtime hook
   `rdmaSetUserBridgeInstaller`; `installRdmaComposeBridge` then invokes it to add the
   user's `createXxx`/functions/statics/widgets to the shared `RDMA` namespace

The generic runtime AAR ships `librdma_runtime.so` (Hermes + JNI + base Compose protocol:
`RdmaComposerProxy`, state/lambda proxies) plus public headers (`RdmaCompose.h`,
`ListHandle.h`, `RdmaVtable.h`, `jsi/`) exported as a prefab.

### `:rdma-app-gradle-plugin`

Gradle plugin applied to the user's app module. It owns all the app-side wiring, so the
user does not need a dedicated bridge module nor any hand-written native/asset config:

- adds the dependencies (`:kernel`, `rdma-runtime-android`, `hermes-android`)
- writes `UserBridge.kt` (`System.loadLibrary("rdma_user")` + `nativeInstall()`),
  `UserBridgeJni.cpp` (JNI glue) and a `CMakeLists.txt` into `build/generated/rdma/`
- configures the app's `externalNativeBuild` (CMake), `prefab = true` and the
  `pickFirsts` for the framework's native libs
- registers `copyGeneratedCpp` (kernel build output → app) + `invalidateCmake`
- adds the generated `RdmaWidgetEntries.kt` and `UserBridge.kt` to the app's Kotlin sources
- copies the compiled plugin JS into the app's assets; with `rdmaHermesc` set it
  AOT-compiles the JS to Hermes `.hbc` bytecode instead

Configuration (via `gradle.properties`): `rdmaKernelPackage` (default `com.example.kernel`),
`rdmaKernelProject` (default `:kernel`), `rdmaPluginProject` (default `:plugin`),
`rdmaHermesc` (optional path to the Hermes compiler).

**Why the split exists:** the runtime (`librdma_runtime.so`) is a fixed, reusable AAR
(Hermes + JNI + base Compose protocol), while the `@RDMA` glue is per-project. Compiling
it into a separate `librdma_user.so` keeps the runtime publishable once and lets each app
ship only its own generated bridge, wired in through the `rdmaSetUserBridgeInstaller` hook.

### `:plugin`

KMP module with a JS target. Contains the **original** plugin code in
`src/kotlin` (pure JVM source; there is no hand-written `src/jsMain`). The
plugin imports kernel widgets and uses them as ordinary `@Composable`:

```kotlin
import com.example.kernel.Text
import com.example.kernel.runRdmaApp

@Composable
fun App() { /* ... */ }
fun main() { runRdmaApp { App() } }
```

This original code is compiled in two passes:

1. **Resolve pass** (JVM): `src/kotlin` compiles the original source against `:kernel`; the FIR plugin resolves `@RDMA` classes and `@RDMA`+`@Composable` widget usages and emits `*_rdma.kt` into `build/generated/rdma/`.
2. **JS pass**: `jsMain` points only at `build/generated/rdma/`, which also contains the generated `RdmaRuntimeBridge.kt`/`RdmaWidgetBridge.kt`, and compiles it to JavaScript.

Output: `RDMAHermes-plugin.js` (webpack bundle).

### `:androidApp`

Android entry point. `MainActivity`:
1. Registers the user bridge via `UserBridge.nativeInstall()`
2. Initializes Hermes runtime via `RdmaBridge.nativeInit()` (async — starts the Hermes thread)
3. Loads `kotlin-kotlin-stdlib.js` + other deps (required by Kotlin/JS output)
4. Loads `RDMAHermes-plugin.js` (compiled plugin)
5. Polls `nativeIsReady()` and, once ready, `setContent { RdmaComposeHost.Content() }`

### `:rdma-tests`

JVM integration tests (no Android device). They drive `CppGenerator` /
`RdmaWidgetGenerator` directly with `RdmaClassInfo` fixtures and assert on the
generated C++ (proxy files, JNI cache, vtable setup, widget bridge marshaling).
